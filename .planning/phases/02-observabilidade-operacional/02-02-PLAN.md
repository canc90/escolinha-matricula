Fatos do terreno já confirmados neste ambiente (não redescobrir):
- Não há PHP/Composer no host: `cd laravel && docker compose exec -T app php artisan ...`, `... ./vendor/bin/pint`. `laravel/tinker` está instalado (usado pelos verifies).
- **Onde plugar o 5xx (investigado no vendor, `Illuminate/Foundation/Exceptions/Handler.php`)**: `Handler::report()` roda `ReportableHandler`s apenas para exceções que passam por `shouldntReport()`, e `internalDontReport` inclui `HttpException`, `ValidationException`, `AuthenticationException` — ou seja, um `abort(503)`/`abort(500)` (que é `HttpException`) NÃO chega em `report()`. Já `Exceptions::respond($using)` registra `Handler::respondUsing()`, cujo callback `finalizeResponseCallback` é chamado em `finalizeRenderedResponse($response, $e, $request)` ao FINAL de `Handler::render()`, com a resposta HTTP já renderizada — logo ele vê o STATUS REAL (5xx de exceção, inclusive `abort`), funciona igual para web e para API (mesmo caminho de render) e recebe a exceção para o contexto. É por isso que a captura é por `respond()`, e NÃO por `report()` nem por um listener de log nem por um handler Monolog (esses dois últimos veriam só o log, não o status, e disparariam para erro não-HTTP/console).
- O callback de `respond()` recebe `($response, $e, $request)` e o valor devolvido SUBSTITUI a resposta — devolva `$response` inalterada. Ele roda dentro do ciclo da requisição: qualquer `throw` ali quebraria a página de erro, então `notificar()` engole tudo.
- Prova de mecanismo executada neste ambiente: `app(Illuminate\Contracts\Debug\ExceptionHandler::class)->render(Illuminate\Http\Request::create('/x','GET'), new RuntimeException('...'))` devolve status 500 a partir do tinker — é assim que o verify dispara um 5xx REAL de ponta a ponta sem rota de sonda em produção; e um receptor `php -S 127.0.0.1:9977` no container recebe o POST JSON do Http client (`{"status":500,...}`) — mecanismo do verify confirmado.
- As variáveis de ambiente inline vencem o `.env` (o `variables_order` do container é `EGPCS` e o repositório do Dotenv é imutável): `ALERT_WEBHOOK_URL=... php artisan ...` dentro de `docker compose exec -T app sh -c '...'` funciona e é como o verify troca de canal sem editar `.env`. O `.env` de dev NÃO é versionado e NÃO pode ser lido daqui (guarda de segredo): nunca imprima o `.env`.
- `Http::post($url, $array)` envia JSON por padrão no Laravel (confirmado com o receptor local) — um `POST` com `["status" => 500]` chegou como `{"status":500}`.
- `CACHE_STORE=array` no comando deixa o cache (dedup/teto) em MEMÓRIA e zerado a cada processo: é o que torna o verify idempotente (repetir o mesmo verify não é suprimido pela deduplicação de 10 minutos). Os testes usam `CACHE_STORE=array` pelo `phpunit.xml`.
- Rotas registradas DENTRO de um teste são casadas normalmente, e uma exceção lançada nelas é RENDERIZADA (a resposta chega com status 500) — confirmado executando um teste de sonda fora do repositório. É assim que a suíte cria o 5xx sem poluir `routes/web.php`.
- `tests/TestCase.php` é vazio (só estende a base); não existe `tests/Pest.php`; a suíte é PHPUnit (classes, métodos `test_...`). `Http::fake()`/`Http::assertSent` são usados em `tests/Feature/AiEducacionalTest.php`. `pint --dirty` NÃO funciona no container (não há `.git` ali).
- Em produção: `APP_DEBUG=false`, `QUEUE_CONNECTION=database`, `LOG_LEVEL=warning`; não há SMTP confiável (`MAIL_MAILER=log`), por isso o canal é webhook HTTP e não e-mail.
- O `.gitignore` do `laravel/` ignora `.env` e `.env.production` (a URL do webhook, se contiver token, fica fora do versionamento) e ignora `*.log`.
